# ADR: Canonical Notification Architecture

**Status**: Accepted (this pass). **Date**: 2026-07-22. **Ticket**: 8 (Notification Center), canonical-architecture pass.

This ADR describes the *actual* code found by a full call-graph audit of this repository, not a generic notification-architecture pattern. Every claim below was verified by reading the real source (grep + file reads), not assumed from naming or prior summaries.

## 1. Current state (before this pass)

Three independent, code-level-disjoint in-app notification paths existed:

1. **`platform_notifications`** (table) / `PlatformNotification` (model) — written exclusively by `SendPlatformNotificationJob`, dispatched exclusively by `NotificationService::send()` (44 scenario methods, 67+ call sites across `app/`, all funneling through one static entry point). Read by `NotificationController` (the web Notification Center — search/filters/pin/archive/bulk, all built in prior Ticket 8 passes) and by `NotificationPreference`-aware dedup/preference enforcement.
2. **Laravel's built-in `notifications` table** (standard `morphs('notifiable')` + `data` JSON blob) — written by two independent producers:
   - `App\Jobs\SendNotificationJob` — a small queued job with its own docblock-documented usage example.
   - `App\Services\NotificationDispatcher::dispatchInApp()` — a separate multi-channel dispatcher (in_app/email/whatsapp) that wrote directly to `$user->notifications()->create(...)`.
   Read by `MobileController::notifications()` / `markNotificationRead()` (the mobile API).
3. **`App\Services\NotificationDispatcher`** — also the real integration point for WhatsApp (`SendWhatsAppJob` → Twilio/Meta providers, genuinely implemented) and templated email (`NotificationTemplate::render()` + `SendEmailJob`). Its in-app branch was store #2 above; its WhatsApp/email branches are a legitimate, separate multi-channel concern, not a duplicate in-app store.

## 2. Three-store problem — audited, with corrected evidence

The ticket brief for this pass assumed `SendNotificationJob` had two live callers, `GenerateReportJob` and `IssueCertificateJob`, and that `NotificationDispatcher`'s live relationship to the canonical flow was merely "unclear." **The audit found a stronger, more specific problem than assumed:**

- `grep -rln "IssueCertificateJob::dispatch" app/` → **zero matches outside the job's own docblock.** `IssueCertificateJob` has never been dispatched anywhere in this codebase. The real, live certificate-issuance notification path is `CertificateAutomationService`/`CertificateService` calling `NotificationService::certificateIssued()` directly (pre-existing, confirmed by earlier tickets' passes) — `IssueCertificateJob` was always dead, parallel scaffolding.
- `grep -rln "GenerateReportJob::dispatch" app/` → **zero matches outside the job's own docblock.** Same conclusion: never dispatched.
- `grep -rln "SendNotificationJob::dispatch" app/` → exactly the two calls above, both inside dead jobs. **`SendNotificationJob` therefore has zero live callers, transitively.**
- `grep -rln "NotificationDispatcher::class\)" app/` → exactly one call site: `AutomationEngineService::actionInApp()`.
- `grep -rln "AutomationEngineService"` (usages outside its own file) → **zero.** `AutomationEngineService::handle()` — the only public entry point that could ever trigger `actionInApp()` — is never called by any controller, event listener, or scheduled command in this codebase. It is fully dormant, matching the exact "documented, unused scaffolding" pattern this recovery document has already found elsewhere (e.g. `CertificateAutomationService::issueForManualCompletion()` in the Ticket 1 pass).

**Corrected conclusion**: the built-in `notifications` table has **zero live writers** in the current codebase. `MobileController::notifications()` (routed, real, reads that table) has therefore always returned an empty list in practice — a genuinely broken/stub feature, not a populated second inbox needing careful data reconciliation. This changes the risk profile of consolidation significantly: there was no live data-loss risk in migrating the mobile endpoint, and the "migrate two live callers" step of the original brief instead became "the two named callers were never live; fix them anyway for correctness and turn off the class of bug."

Zero test coverage existed for `NotificationDispatcher`, `SendNotificationJob`, `AutomationEngineService`, or `MobileController`'s notification methods prior to this pass — independently confirming they were never exercised as "the" live path.

## 3. Canonical store decision

**`platform_notifications` (via `PlatformNotification`) is the canonical, sole in-app notification store.** It already has 67+ live producers, the Notification Center UI, preference enforcement, dedup, and pin/archive/search/bulk actions built on it. The built-in `notifications` table is not deleted (Laravel core features — e.g. any future `Notifiable`/`->notify()` usage for password resets, which is unrelated to this domain and stays on that table by design) but is no longer written to by any in-app-notification producer in this codebase.

## 4. Canonical dispatcher decision

**`NotificationService::send()` is the single canonical entry point for in-app notifications** — unchanged from the pre-existing architecture, now reinforced: `NotificationDispatcher::dispatchInApp()` no longer writes directly to the built-in table; it now calls `NotificationService::send()` (see §6). `SendNotificationJob` is `@deprecated`, not deleted (see §10), with zero remaining live callers after this pass.

## 5. Canonical preference source

**`NotificationPreference` remains the sole preference source**, unchanged. `SendPlatformNotificationJob::excludeUsersWhoDisabledThisType()` (fixed in the prior Ticket 8 pass) is the sole enforcement point for the `in_app` channel. `NotificationDispatcher::send()`'s own `NotificationPreference::isEnabled()` check (pre-existing, for email/whatsapp channel selection) is unaffected — it still gates whether `dispatchChannel()` is even called per channel, and now the `in_app` branch's actual write additionally goes through the canonical preference-aware `SendPlatformNotificationJob`, so an in-app notification triggered via `NotificationDispatcher` is now double-consistent with the same preference row two different ways it wasn't in conflict about before (both checks agree by construction, since they read the same table).

## 6. Web consumer decision

Unchanged — `NotificationController` (`/api/notifications`) is the sole web Notification Center backend, reading `platform_notifications` directly, already complete (prior Ticket 8 passes).

## 7. Mobile consumer decision

**`MobileController::notifications()` / `markNotificationRead()` migrated to read/write `platform_notifications`** (Option A — response-shape adapter, not a versioned breaking change): the item shape (`id`, `type`, `notifiable_type`, `notifiable_id`, `data.{type,title,message,url}`, `read_at`, `created_at`) is preserved so any existing mobile client parsing that contract keeps working; `id` is now the numeric `platform_notifications.id` instead of a UUID (the only field whose *type* changed — the built-in table's UUID was never really meaningful to a client beyond "an opaque identifier to send back for mark-read," which numeric IDs also satisfy). `?archived=` items are excluded from the mobile list by the same convention as the web center. `unread` in the response `meta` now matches the web `unread_count` exactly, proven by a direct cross-endpoint test. Ownership scoping (`where('user_id', ...)`) is unchanged in spirit, now enforced against the correct table.

## 8. WhatsApp integration decision

**Not rebuilt, not rewired end-to-end this pass** (explicitly out of scope per the ticket brief's Step 9 exception). `NotificationDispatcher::dispatchWhatsApp()` → `SendWhatsAppJob` → Twilio/Meta providers is untouched and remains the correct, real integration point. The only change to `NotificationDispatcher` this pass is removing its duplicate in-app write path (§6) — its WhatsApp and email branches, and the `NotificationTemplate`-driven rendering they depend on, are unmodified. Per-channel preference enforcement for WhatsApp already exists via `NotificationPreference::isEnabled($user->id, 'whatsapp', $type)` inside `NotificationDispatcher::send()`, gating channel selection before `dispatchWhatsApp()` is ever called — this was already correct and required no change.

## 9. Email channel relationship

Two genuinely separate email mechanisms coexist by design, confirmed by reading both:
- **Domain-notification email**: `NotificationDispatcher::dispatchEmail()` — templated (`NotificationTemplate::render($type, 'email', ...)`), only sent when a template exists for that type, independent of whether an in-app row was also created (a template-render failure for email does not prevent `dispatchInApp()`/`NotificationService::send()` from running, since `dispatchChannel()` calls each channel independently per the `foreach ($channels as $channel)` loop in `send()`).
- **Transactional mail** — sent from inside the same scenario methods that also call `self::send()` for the in-app row, via two mechanisms confirmed by direct read: some scenarios (`accountCreated`, `studentRegistered`, etc.) import and dispatch `App\Mail\*` classes directly (`WelcomeMail`, `CourseEnrollmentMail`, `CourseCompletionMail`, ...); `assignmentGraded()` (read in full for this ADR) instead calls `EmailService::dispatch('assignment_graded', ...)` after its `self::send()` call, gated by `$student?->email` being present. Both mechanisms share the same pattern: one domain scenario method coordinates both channels sequentially in its own body, each channel's dispatch is independent (an email failure does not roll back or block the already-dispatched in-app `send()` call, since `self::send()` already returned), and there is no shared transaction or shared failure path between them. This is the "one domain scenario coordinates both channels, channel-specific delivery stays separate" pattern the ticket brief asked for — it was **already the existing architecture**, not something this pass needed to build. No redesign of the existing `Mail`/`EmailService`/`NotificationLog`/email-monitoring system was made or was needed.

## 10. Migration strategy

Additive only. One new migration this pass: `2026_07_22_010001_add_idempotency_and_legacy_source_to_platform_notifications.php` — two nullable columns (`idempotency_key`, `legacy_source_id`) plus two indexes, fully reversible (`down()` drops both). No column was renamed or removed on `platform_notifications`, `notifications`, `notification_preferences`, or any other notification-related table.

## 11. Backward compatibility

- `NotificationService::send()`'s signature is unchanged; `idempotency_key` is an **optional** key inside the existing `$extra` array, so all 44 pre-existing scenario methods and their 67+ call sites are unaffected — they simply don't pass it, and dedup falls back to the pre-existing time-window+lock behavior exactly as before (proven by `test_omitting_idempotency_key_preserves_the_original_time_window_dedup_behavior`).
- `MobileController`'s response envelope (`{success, data, meta}`) and per-item field names are unchanged; only `data[].id`'s underlying type changes from UUID string to a numeric-string, which was never guaranteed as a UUID by the endpoint's own contract (no client-facing documentation asserted a UUID format).
- `IssueCertificateJob`/`GenerateReportJob` keep their public constructor signatures (`dispatch($certificate)` / `dispatch($report, $requestedBy)`) unchanged — only their internal notification call was swapped from the deprecated job to the canonical scenario method.

## 12. Rollback strategy

- The new migration is a clean `down()` — drop the two columns/indexes, no data loss beyond the (optional, always-nullable) values in them.
- The `MigrateLegacyNotificationsCommand` never deletes source rows in the built-in `notifications` table, and every row it creates in `platform_notifications` is tagged via `legacy_source_id`; a rollback of the migrated data (if ever needed) is `DELETE FROM platform_notifications WHERE legacy_source_id IS NOT NULL` — safe and reversible without touching the untouched source table.
- Code-level rollback (reverting `NotificationDispatcher`/`MobileController`/the two jobs to their pre-pass state) is a plain git revert; nothing in this pass makes that unsafe, since the built-in table and its rows (if any) were never deleted.

## 13. Data-retention decision

Unchanged from the pre-existing `emc:prune-notifications` command (deletes read `platform_notifications` older than N days, default 90). No retention policy was added or changed for the built-in `notifications` table — it is out of scope now that nothing writes to it going forward, and any legacy rows already migrated remain in both places (source untouched, copy in the canonical store) until a future, separate decision to prune the legacy table itself.

## 14. Read/unread synchronization

There is now exactly one `is_read`/`read_at` source of truth (`platform_notifications`) for both consumers. `MobileController::markNotificationRead()` sets both fields on the same row the web Notification Center reads — mark-read from either surface is immediately visible on the other, proven by `test_mobile_unread_count_matches_the_web_notification_center` (asserts the two endpoints' unread counts are numerically identical after mixed read/unread rows).

## 15. Dedup/idempotency direction

Two-tier, backward-compatible, per Step 11's fallback-tier design:
1. **Explicit `idempotency_key` (opt-in)** — deterministic `(user_id, type, idempotency_key)` lookup inside the same `DB::transaction()` + `lockForUpdate()` used by the existing dedup check. Immune to timing entirely for callers that supply it (proven: exact-duplicate-key → 1 row; distinct-key → 2 rows; per-recipient isolation in a batch send; survives 3x retry of the same key without duplicating).
2. **Time-window fallback (unchanged, default)** — every scenario method that doesn't yet pass an `idempotency_key` keeps the exact pre-existing `(user_id, type, entity_id, 10-second window)` + row-lock behavior from the prior Ticket 8 pass, unmodified.

No universal weak key (e.g. always `user_id+type+entity_id`) was invented, per the explicit instruction not to do so — a single entity can legitimately trigger the same notification type more than once over its lifecycle (e.g. a resubmitted assignment), and forcing a single implicit key would silently swallow the second, legitimate notification.

**Adoption status — RESOLVED as of the deterministic-idempotency completion pass.** All 49 scenario methods were individually read and classified as A (deterministically idempotent), B (legitimately repeatable, time-window dedup is the correct tool), or C (legitimately repeatable, needs a distinct per-occurrence key), full detail in `docs/architecture/NOTIFICATION_EVENT_MATRIX.md`. A fresh, careful re-audit of that classification (re-parsing the matrix's own table, not trusting an earlier pass's prose summary) found the true Class A/C count is **36**, not the "26" an earlier pass's summary line claimed — a correction made honestly, not a new discrepancy. Of those 36: 6 were wired in the prior pass (`certificateIssued`, `reportReady`, `assignmentCreatedForStudents`, `assignmentGraded`, `sessionScheduled`, `materialVisible`); **the remaining 30 were wired in the deterministic-idempotency completion pass**, via a new canonical builder, `App\Services\NotificationIdempotencyKey` (one static method per real key shape — `forEntity`, `forEntityWithComponent`, `forStatusTransition`, `forScheduleChange`, `fromComponents` — never a generic event framework), each individually tested. **Zero deterministic gaps remain**: every scenario genuinely requiring a stable key now has one; the 13 Class B scenarios correctly remain on the time-window fallback by deliberate design. No caller signature changes were required anywhere — every key was built from parameters each method already received.

Two explicit, documented legitimate-repeat product decisions were made while adopting the remaining 30 (not hidden as silent behavior): (1) `moduleActivated`/`lessonActivated` key on the module/lesson id alone — only the *first* activation notifies a given recipient; a later deactivate/reactivate cycle is treated as the same occurrence, since the schema has no activation-version column to key on instead (a future pass wanting reactivation to notify again must add one first). (2) Six scenarios that receive no database entity id at all (only display names/titles — `placementTestCompleted`, `classGroupAssigned`, `classGroupStudentAssignedInstructor`, `oralAssessmentCompleted`/`StatusChanged`/`Rescheduled`) key on the best available real, already-passed name/title parameters; a named, accepted name-collision limitation (two students/classes sharing an identical display name would collide) rather than widening these methods' signatures and updating every caller for this pass.

## 16. Push, SMS, realtime, and quiet-hours — implemented this pass (definitive completion pass)

The prior pass deferred these entirely, per that pass's own explicit scope limit. This pass implements all four, real and tested, each disabled-by-default so no existing deployment's behavior changes until it opts in via configuration.

**Push — Web Push (VAPID), not Firebase/FCM.** Evidence-based choice: the audit found zero Firebase config, no `google-services.json`, no mobile app in this repo — nothing to justify an FCM dependency. Standard Web Push (RFC 8030) via `minishlink/web-push` (a real, actively maintained composer package, installed this pass) works across Chrome/Firefox/Edge with no third-party account required, only a locally-generated VAPID keypair (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`, both empty by default → `WebPushNotificationService::isConfigured()` is false → every send is a safe, logged no-op, zero network calls). `push_subscriptions` table (new migration) stores one row per browser/device subscription, ownership-scoped via `PushSubscriptionController` (register/list-state/remove, all `user_id`-scoped). Invalid/expired subscriptions (410/404 per spec, surfaced by the library's `MessageSentReport::isSubscriptionExpired()`) are deleted automatically on the next send attempt, never left to retry forever. Frontend: `src/lib/push.ts` (subscribe/unsubscribe via the browser `PushManager` + a minimal `public/sw.js` service worker), wired into a new panel on `NotificationPreferencesPage.tsx`, itself disabled in the UI when `VITE_VAPID_PUBLIC_KEY` is unset.

**SMS — Twilio, with its own dedicated credentials.** Mirrors the pre-existing WhatsApp provider pattern exactly (`SmsProvider` interface, `LogSmsProvider` default/safe, `TwilioSmsProvider` real): `config/sms.php` uses `SMS_TWILIO_*` env vars, deliberately never reusing `WHATSAPP_TWILIO_*` — a Twilio account authorized for the WhatsApp sandbox is not automatically authorized for plain SMS, and conflating them would risk a silent, confusing failure in whichever environment actually has one but not the other. `SmsNotificationService::isValidE164()` rejects any non-E.164 number before ever reaching the provider (tested), and `NotificationLog` (the pre-existing delivery-log table — reused, not duplicated) records every attempt.

**Realtime — Laravel Reverb.** Chosen over Pusher/Ably/Soketi because it is first-party, free, and self-hosted (`composer require laravel/reverb`, installed this pass) — no third-party account or recurring cost, consistent with every other channel's "disabled by default, real when configured" posture. `BROADCAST_CONNECTION` defaults to `null` (framework's built-in no-op driver) everywhere (`.env`, `.env.example`, `phpunit.xml` already had it) — real broadcasting only activates once `BROADCAST_CONNECTION=reverb` and a `php artisan reverb:start` process is actually supervised in production. Every `platform_notifications` row, from every one of the 49 scenarios, now broadcasts a `PlatformNotificationCreated` event on a private `notifications.{userId}` channel (`routes/channels.php`, ownership-checked identical to the framework's default `App.Models.User.{id}` channel) the moment it's created inside `SendPlatformNotificationJob` — centrally, once, not per-scenario. The channel-authorization HTTP endpoint (`/broadcasting/auth`) is exposed a second time at `/api/broadcasting/auth` under `auth:sanctum` with an explicit `guards => ['sanctum']` (the framework's default registration uses the `web` session guard, useless for this Bearer-token-only SPA — discovered and fixed this pass, proven by a dedicated ownership test that initially failed against the wrong guard before the fix). Frontend: `src/lib/echo.ts` (Laravel Echo + Pusher-protocol client, since Reverb speaks the Pusher protocol), wired into `DashboardLayout.tsx` to prepend new notifications instantly; the pre-existing 90-second poll is kept unconditionally as the graceful fallback for when realtime is unconfigured or the socket drops — the frontend never assumes realtime is available.

**Quiet hours — global per-user, delay-not-discard.** One row per user (`notification_quiet_hours`, new table) rather than per-channel/type — the smallest schema that satisfies the requirement (deployable UI: `enabled`, `start_time`, `end_time`, `timezone`), extensible to a finer grain later without a breaking migration if ever needed. Exact policy (`QuietHoursService`'s own docblock is the source of truth): **in-app notifications are always written immediately**, quiet hours or not — a user opening the Notification Center during their own quiet hours must still see what happened; **only SMS and push** (the genuinely disruptive channels) are delayed to the configured end time via `->delay()` on the queued job, computed with real Carbon calendar-date construction in the user's configured timezone (not a fixed-offset second count), so overnight ranges (`22:00→07:00`) and DST transitions resolve correctly — proven by dedicated same-day/overnight/timezone tests. A caller may pass `$extra['urgent'] = true` to bypass quiet hours entirely for a specific send (available, not yet wired to any specific scenario — no current scenario was judged genuinely time-critical enough to warrant it without a product decision).

## 17. External-channel failure strategy and idempotency-adoption limitation (honest gap)

SMS/push failures never affect the already-created in-app row — each channel's job runs and fails independently after the canonical write already succeeded, logged via the pre-existing `NotificationLog` table (channel/status/error_message/sent_at), the same table WhatsApp already used — no new logging subsystem was built, per the explicit instruction to reuse existing logging patterns rather than invent an admin subsystem.

**RESOLVED as of the deterministic-idempotency completion pass**: all 36 scenarios that genuinely warrant a deterministic `idempotency_key` (Class A/C in the event matrix, a count corrected from an earlier pass's undercounted "26") now have one adopted, individually tested. See §15 for the full adoption reasoning and the two explicit legitimate-repeat product decisions made along the way. The remaining Ticket 8 gap is unrelated to idempotency — see §20 (per-scenario SMS/push channel-policy adoption).

## 18. Rejected alternatives and why

- **Delete the built-in `notifications` table / `SendNotificationJob` outright.** Rejected — even with zero *currently known* live callers, deleting infrastructure Laravel itself may use for other `Notifiable` features (e.g. `ResetPasswordNotification`, confirmed still in use via `User::notify(new ResetPasswordNotification($token))`, unrelated to this domain but sharing the same table) would be a real, unnecessary regression risk for zero benefit. Deprecating in place (§10) achieves the same "stop the class of bug" outcome without that risk.
- **Force every `NotificationDispatcher::send()` call through `NotificationService::send()`'s exact signature (title/message strings), replacing template rendering.** Rejected — `NotificationTemplate::render()` is a genuinely different, admin-configurable content system (see `NotificationTemplateController`) serving a different need (per-type, admin-editable message templates) than the 44 hardcoded-string scenario methods. Collapsing them would be a much larger, riskier redesign than "stop writing to a second table," and was not requested.
- **Rewrite `AutomationEngineService`/`NotificationDispatcher` into `NotificationService` entirely.** Rejected — `NotificationDispatcher` provides real, separate value (multi-channel selection logic with `NotificationPreference` gating per channel, WhatsApp/email routing) that `NotificationService` does not have and does not need to duplicate; per the brief's own Step 8 instruction, "do not create a second NotificationService" — the fix was narrowly scoped to removing only the duplicate in-app persistence branch.
- **A single universal weak idempotency key for all 49 scenarios.** Rejected — see §15.
- **Firebase Cloud Messaging for push.** Rejected — no existing Firebase project/credentials, no mobile app in this repo to justify the dependency; standard Web Push covers every real target (web browsers) with a self-hosted, no-account keypair. FCM remains a reasonable future choice if/when a native mobile app is built and needs native push.
- **Pusher or Ably (hosted) for realtime.** Rejected in favor of Reverb — both are legitimate, but both are paid, third-party-hosted services; Reverb is first-party, free, self-hosted, and protocol-compatible with the same `laravel-echo`/`pusher-js` frontend client, so switching to a hosted provider later (if self-hosting Reverb becomes operationally undesirable) is a config-only change, not a rewrite.
- **Per-channel/per-type quiet hours (finer grain) on day one.** Rejected for this pass — a single global per-user window is the smallest schema satisfying "quiet hours support," reversible/extensible later; building the finer-grained version first would be speculative complexity with no current product requirement asking for it.

## 19. Deployment requirements (this pass's new infrastructure)

- **Migrations**: `2026_07_22_010001_add_idempotency_and_legacy_source_to_platform_notifications.php` (prior pass), `2026_07_23_010001_create_notification_quiet_hours_table.php`, `2026_07_23_010002_create_push_subscriptions_table.php` (this pass) — all additive, all reversible via `php artisan migrate:rollback`.
- **Queue workers**: unchanged requirement — `SendSmsJob`/`SendPushJob` are `ShouldQueue` like every other notification job; a real queue worker (not `sync`) is required in production for them to run off the request thread, exactly as already required for `SendPlatformNotificationJob`.
- **New process — Reverb server**: `php artisan reverb:start` must run as a supervised background process (e.g. via Supervisor, matching how queue workers are already supervised) for realtime to function. Until it is deployed and `BROADCAST_CONNECTION=reverb` is set, the frontend silently and correctly falls back to the pre-existing 90-second poll — deploying the rest of this pass's code with Reverb *not yet running* is safe and was the default state throughout this pass's own testing.
- **Environment variables** (backend `.env`, all optional/empty-safe): `BROADCAST_CONNECTION`, `REVERB_APP_ID`, `REVERB_APP_KEY`, `REVERB_APP_SECRET`, `REVERB_HOST`, `REVERB_PORT`, `REVERB_SCHEME`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, `SMS_PROVIDER`, `SMS_TWILIO_SID`, `SMS_TWILIO_TOKEN`, `SMS_TWILIO_FROM` — all documented with inline comments in `.env.example`.
- **Frontend variables** (`.env`, all optional/empty-safe): `VITE_REVERB_APP_KEY`, `VITE_REVERB_HOST`, `VITE_REVERB_PORT`, `VITE_REVERB_SCHEME`, `VITE_VAPID_PUBLIC_KEY`.
- **Service worker**: `public/sw.js` (new, minimal — push display + notification-click only, no offline caching) must be served from the site root for the Web Push subscription flow to register correctly; no build step required, Vite serves `public/` as-is.
- **VAPID keypair generation**: `php artisan tinker` → `Minishlink\WebPush\VAPID::createVapidKeys()`, or any standard `web-push generate-vapid-keys` CLI — a one-time, self-hosted operation, no external account.
- **Rollout order**: (1) deploy backend migrations + code (safe — every new feature is disabled by default); (2) deploy frontend (safe — realtime/push UI self-disables when their env vars are empty); (3) only once both are live and stable, optionally enable Reverb (`reverb:start` + `BROADCAST_CONNECTION=reverb` + matching frontend `VITE_REVERB_*`) and/or generate a VAPID keypair and set `SMS_PROVIDER=twilio` with real credentials — each is independently toggleable, none blocks the others.
- **Rollback plan**: set the relevant env var(s) back to their safe defaults (`BROADCAST_CONNECTION=null`, `SMS_PROVIDER=log`, clear `VAPID_*`) to instantly disable a channel without a code deploy; migrations roll back cleanly if the schema itself needs to be reverted.

## 20. Channel-policy gap — closed this pass

Deterministic idempotency (§15) was fully resolved in the prior pass. The remaining gap described here previously — "only 2 of 49 scenarios opt into sms/push, the other 47 need a real per-scenario product decision" — is now closed by `App\Support\NotificationChannelPolicy` (§21). Re-auditing the actual source this pass found the "2 proof-of-concept scenarios" characterization was itself inaccurate: `grep -n "'channels' =>" app/Services/NotificationService.php` returns zero matches — neither `assignmentGraded` nor `certificateIssued` (nor any other scenario) has ever hardcoded a `channels` key. Both simply fell through to no external fan-out at all prior to this pass, since `SendPlatformNotificationJob::fanOutToExternalChannels()` previously required an explicit `$extra['channels']` with no default. This section is kept (not deleted) as an honest record of the prior pass's own documentation drift.

## 21. Channel policy — `NotificationChannelPolicy` (Ticket 8 channel-policy completion pass)

**Decision**: a single static, code-controlled class (`App\Support\NotificationChannelPolicy`), not a database table, is the source of truth for which channels each of the 49 real dispatched notification `type` strings defaults to. Rationale: channel policy is a product decision that should be reviewable in a PR diff and covered by the completeness test below — not editable ad hoc by a database row, and not something that should silently drift from what's actually tested.

**Design principles applied to all 49 types**:
- `in_app` is the only channel every scenario gets automatically, and is the only channel never delayed by quiet hours.
- `push` is added only where missing the notification for a few hours would materially reduce its usefulness (a real schedule change, a graded result, a completed achievement, a confirmed paid action, a booked appointment) — 7 of 49 types.
- `sms` is reserved for a small, explicitly time-sensitive subset and is never added merely because an event is "important". Only two types resolve it, and only contextually: `session_scheduled` (reschedule of an existing plan, not a brand-new session) and `oral_assessment_rescheduled`, both gated on the real `starts_at`/new-slot parameter the calling method already has being within `NotificationChannelPolicy::IMMINENT_THRESHOLD_HOURS` (24h) of now — never by parsing title/message text.
- `urgent` (quiet-hours bypass) is `false` for all 49 types. Candidates considered and rejected: `course_cancelled` (courseCancelled(courseId, courseTitle)'s signature has no timing parameter, so "how soon" can't be verified — treated as push-worthy but not urgent); `oral_assessment_rescheduled`/`session_scheduled` even when imminent (a reschedule notice benefits from SMS reach, but nothing about it is an operational emergency that justifies waking someone during their configured quiet hours). No scenario method in the current codebase carries a verified emergency signal.
- `email`/`whatsapp` are tracked per-type (`existing_separate` vs `none`) purely so the policy documents, rather than duplicates, the ~8 scenarios that already have a confirmed separate `EmailService::dispatch()`/mail call site (e.g. `student_registered` → `CourseEnrollmentMail`, `certificate_issued` → certificate-ready email, `learning_path_enrolled`/`learning_path_completed` → their respective mails). The channel policy has no email/WhatsApp channel of its own — `NotificationChannelPolicy::KNOWN_CHANNELS` is exactly `[in_app, push, sms]` — so it structurally cannot double-dispatch an email that another code path already sends.

**Wiring** (Option A — central, in the job, not per-scenario): `SendPlatformNotificationJob::fanOutToExternalChannels()` resolves `$this->extra['channels'] ?? NotificationChannelPolicy::resolveWithContext($this->type, [...])` and `$this->extra['urgent'] ?? NotificationChannelPolicy::isUrgent($this->type)`. Any scenario method can still override either via `$extra['channels']`/`$extra['urgent']`, unchanged from the pre-existing opt-in mechanism used throughout Ticket 8 testing — the policy is the default, not the only path.

**Preference interaction** (unchanged semantics, audited this pass): a channel absent from the type's policy is never sent regardless of preference (the preference table only *restricts* an already-policy-permitted channel, it never *grants* one). A channel present in policy still requires `NotificationPreference::isEnabled()` to be true (default true — no row means enabled, unchanged for in_app). Push additionally requires a real `PushSubscription` row; SMS additionally requires `SmsNotificationService::isValidE164($user->phone)`. Verified in `tests/Feature/Ticket8ChannelPolicyTest.php`.

**Production configuration checklist** (supersedes/extends §19's per-channel env vars with the policy layer specifically):
- No configuration is required for the policy itself — it is pure code, ships active, and its in-app/push channel defaults take effect the moment this pass is deployed.
- Deploying this pass **before** `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` are set is safe: `WebPushNotificationService::isConfigured()` returns false, `SendPushJob` becomes a logged no-op, exactly as designed since Pass C — no mass-push risk from missing keys.
- Deploying this pass **before** `SMS_PROVIDER=twilio`/`SMS_TWILIO_*` are set is safe: the default `SMS_PROVIDER=log` provider only writes to `notification_logs`, never places a real call to Twilio — no mass-SMS risk from missing credentials, and no scenario in this policy defaults to SMS unconditionally (only 2 types, contextually, only when genuinely imminent).
- No new migration ships with this pass — the policy reads no new columns and writes no new tables.
- Verify after deploy: confirm no unexpected volume spike in `notification_logs` for `channel = 'push'` on `certificate_issued`/`assignment_graded`/etc. in the first 24h if VAPID is already configured in that environment — expected, not a bug, since those two types now correctly receive push for the first time (see §20).
